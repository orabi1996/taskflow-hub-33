# سجل الأعمال اليومية — المرحلة الأولى

## ما تغير
- تبويب «أعمالي اليومية» داخل `/time`، والقائمة أصبحت «الأعمال والوقت».
- سجل مستقل عن المهام والمؤقتات: تاريخ العمل، العميل، الموديول، نوع النشاط، الوصف، النتيجة، العائق، والمدة الاختيارية.
- المهمة المختارة تورث العميل والموديول؛ لا تُغلق المهمة تلقائيًا عند اعتماد سجل عمل.
- مسودة ← إرسال ← اعتماد أو طلب استكمال ← تعديل وإعادة إرسال.
- الموظف يرى سجلاته. المدير يرى فريقه المباشر وفق `profiles.manager_id`، والإداري والمدير العام يراجعان الموظفين الآخرين. لا اعتماد ذاتي.
- حماية على مستوى PostgreSQL، وسجل تاريخ لكل إنشاء وتعديل، ومنع تعديل السجلات المعتمدة.
- عرض يومي وأسبوعي وشهري وفترة مخصصة، وفلاتر الموظف والعميل والموديول، وتصدير التفاصيل.
- تحميل السجلات والاختيارات على صفحات لتجنب اقتطاع الأرقام عند حد Supabase الافتراضي.
- المجاميع تعكس عدد السجلات والمهام المختلفة التي تم العمل عليها والأيام والدقائق والحالات. لا تمثل درجة إنتاجية أو عدد المهام المكتملة.
- تصحيح نوع خطأ مكوّن router ليتوافق مع `ErrorComponentProps` الذي يقبل `unknown`.

## تفعيل الإصدار
1. اختبر migration `supabase/migrations/20260923220000_daily_work_logs.sql` في بيئة تجريبية مرتبطة بالمشروع.
2. تحقق من تعيين المدير المباشر وحالة الحساب والأدوار للموظفين.
3. جرّب موظفًا ومديره ومديرًا خارج فريقه، ثم نفذ migration على قاعدة الهدف عبر مسار النشر المعتاد.
4. انشر فرع التطبيق بعد تحديث قاعدة البيانات، واختبر التسجيل والإرسال والمراجعة والتصدير بحسابات حقيقية مخولة.

تم تجهيز migration في المستودع؛ لم يتم تطبيقه على قاعدة الإنتاج أو نشر الموقع خلال هذه المرحلة. لا تستلزم الإضافة تعديل بيانات العملاء الحالية. عند فشل النشر يمكن الرجوع لإصدار الواجهة السابق مع الاحتفاظ بالجداول والبيانات الجديدة.

## التحقق
- `node --experimental-strip-types --test tests/work-log-summary.test.ts`
- `PGLITE_MODULE=/path/to/@electric-sql/pglite/dist/index.js node tests/work-logs-rls.mjs`
  يشغّل SQL الحقيقي على PostgreSQL مضمّن مع fixtures محدودة تمثل علاقات المشروع، ويتحقق من العزل والمراجعة وسجل التاريخ والحسابات المعطلة. لا يغني عن اختبار سياسات المشروع الكاملة في staging.
- `npx tsc --noEmit`
- `npm run build`

ملف package-lock الموجود مسبقًا غير متوافق مع package.json؛ لذلك يفشل npm ci. استخدم التحقق المحلي `npm install --ignore-scripts --no-package-lock --no-audit --no-fund` دون تغيير lockfile في هذا التعديل. يلزم توحيد مدير الحزم وملف القفل في تغيير مستقل قبل اعتماد تثبيت CI قابل للتكرار.

## فجوات المشروع التي يجب معالجتها لاحقًا
- العملاء حاليًا تابعون للمشاريع (`clients.project_id` إلزامي)، وليسوا سجلًا مؤسسيًا موحدًا؛ يلزم تصميم نقل وربط دون دمج عملاء اعتمادًا على الاسم فقط.
- الموديولات تستخدم `company_modules` الموجود؛ لا تُفترض قائمة منتجات أو أقسام جديدة.
- لا توجد بعد دورة اعتماد يوم كامل أو حساب أيام العمل والإجازات. الاعتماد في هذه المرحلة لكل سجل.
- لا توجد بعد بطاقة KPI موزونة، أهداف حسب الوظيفة، نسب قبول من أول مرة، أو ترتيب موظفين. تتطلب تعريفًا معتمدًا ومصادر نتائج موثوقة.
- المؤقتات تبقى مستقلة؛ لا تجمع مدتها مع مدة سجلات العمل حتى لا يتكرر حساب الوقت.
- شاشة تاريخ التعديلات، المرفقات، فلتر القسم، والتجميع داخل صفحة العميل تحتاج توسعة لاحقة. سجل التاريخ محفوظ ومحمي في قاعدة البيانات.
- لا يوجد تحقق بصري أو اختبار مستخدم مسجل الدخول على الموقع الحي في هذه المرحلة.
